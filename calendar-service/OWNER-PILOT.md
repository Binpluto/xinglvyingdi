# 仅所有者账号的日历接入

范围：`pluto.hanna@gmail.com`。未向其他用户开放，未升级 Vercel/Neon 套餐。

## 架构

- 正式入口 `vercel-proxy` 使用现有站点登录验证账号，付费/VIP 状态仍读取原服务端结果。
- 日历服务使用独立 Neon 的 Google 授权和事件表。生产入口只通过服务端 HMAC 调用 `owner-bridge`；不将用户 Cookie、数据库 URL、Google 令牌传给浏览器。
- 两侧 `OWNER_PILOT_BRIDGE_KEY` 通过一次性随机值和 stdin 设置，仓库不含密钥。正式入口开关为 `CALENDAR_OWNER_PILOT=enabled`。
- 正式任务使用原后端真实正整数 ID；`SCAL:<event UUID>` 标识只用于恢复关联，页面不显示。同步不自动完成任务，不自动发放积分。
- 日期、取消状态及日历标题由 Neon 事件提供，在 **Vercel 正式入口**的任务响应中合并；旧 Sites 原始地址不具备这一覆盖层。原后端不支持更新 due_at，因此暂未迁移其内部按截止日计算的报表逻辑。
- 完成仍走原任务接口，由原后端写入真实完成历史、经验和金币；新增完成账本仅做幂等与恢复，不再独立加分。时序复用同一任务 ID。
- 首次创建任务需先拿持久创建声明；网络结果不确定时只查询旧任务恢复，不自动发第二次创建请求。重复完成由独立唯一声明和原任务 done 状态共同保护。
- 删除日历任务为“暂停显示”而非删除旧后端历史。取消后隐藏未完成任务；已完成记录保留。
- 同名且同时间的旧任务被标记为待人工确认，不猜测合并或删除。

## 限制和验收边界

- 首次真实关联仅“教练学习安排”，未批量导入用户另外选中的其他日历。
- 改期、取消、重复/并发完成、网络丢失响应、时序复用通过模拟网关测试；不通过伪造真实完成来验证积分。
- 必须由用户选择一项真正完成的日历任务（或真实时序记录）进行一次端到端完成验收；未验收前不得声称真实积分发放已验证。
- 测试库服务升级为账号限定桥接；仍不是所有用户的正式后端。自动后台同步未新增，用户在入口里手动同步。
- 后续扩大开放前需独立正式运行角色、计费/试用规则复核、完整报表融合、授权和迁移审计。

## 发布与回退

- 正式入口源分支为 `codex/starcamp-sync`，Vercel Root Directory 为 `vercel-proxy`。
- 日历服务源在此 `calendar-service` 目录，Vercel 单独项目 `starcamp-calendar-test`。不要将其直接部署到正式项目根目录。
- 回退到只读保护：将正式项目 `CALENDAR_OWNER_PILOT` 改为 `readonly` 后重新部署；保持日期覆盖读取并冻结日历任务写入。不要只删除覆盖层，否则旧后端的日历任务没有原生 due_at。所有任务与完成记录均不得批量删除来“回退”。
- 数据库迁移在 `migrations/`，仅允许目标 `starcamp_calendar_test`。
